# Для продвинутых

← [На главную](Home.md)

Эта страница — для тех, кто хочет управлять splify из консоли и понимать движок.

## Командная строка

| Команда | Что делает |
|---------|-----------|
| `splify-doctor` | Диагностика человекочитаемо. `--json` — для инструментов, `--events` — журнал переключений. Код возврата `0` = всё ок. |
| `splify-status` | Краткий снимок текущего состояния. |
| `splify-apply` | Перегенерировать слой nft/dnsmasq из UCI (после ручной правки конфига). |
| `splify-firewall check\|fix <iface>` | Проверить/починить зону брандмауэра туннеля. |
| `splify-disable` | Аварийно увести весь трафик в WAN (выключить разделение). |
| `splify-update-ipsum` / `-ru` / `-domains` | Принудительно скачать списки. |
| `splify-uninstall` | Полная очистка (вызывается при удалении пакета). |
| `logread -e splify` | Лог службы. |

## Конфигурация

Всё лежит в `/etc/config/splify` (формат UCI): секция `global` (режим, интервал,
kill switch, LAN, URL списков, zapret), одна секция `endpoint` на туннель
(`iface`, `priority`, `type`), и опциональные секции `device` (привязка по IP).
После ручной правки выполните `splify-apply`.

Списки скачиваются по URL из полей `ipsum_url` (через VPN), `ru_url` (напрямую,
питает обход DPI) и `vpn_domains_url` / `ignore_domains_url` (домены). Обновление —
ежедневно по cron (≈04:30–04:50) либо вручную командами `splify-update-*`.

## Режимы маршрутизации (детально)

- **blocklist** (по умолчанию) — через VPN едет только сет `ipsum`
  (заблокированные/зарубежные IP); всё прочее — в WAN (с zapret, если включён);
  RU/CN остаётся напрямую.
- **full** — маршрут по умолчанию через VPN; список «напрямую» — исключения.
- **split** — через VPN едут только ваши явные VPN-списки/домены.

## Как устроен движок

Маркировка nftables → `ip rule` → таблица маршрутизации 200 → активный туннель.
Политические цепочки регенерируются из UCI скриптом `splify-apply`; служба
`splify` крутит цикл failover, проверяет здоровье туннелей (`ping` через
кандидата, неразрушающе) и самовосстанавливает IP-сеты. При отказе всех туннелей —
деградация на WAN с zapret, затем на чистый WAN (или блэкхол при kill switch),
с постоянным стремлением вернуться к приоритету #1.

splify управляет **только маршрутизацией** и **никогда не трогает брандмауэр** —
поэтому туннель должен быть в зоне firewall с маскарадингом и пробросом
`lan → зона туннеля` (кнопка «Починить автоматически» делает это за вас).

## Доменная маршрутизация: dnsmasq vs splify-dns

Домены (`vpn_domain`/`direct_domain`, скачанные списки `vpn_domains_url`/
`ignore_domains_url`) должны как-то превратиться в IP-адреса для тех же nft-
сетов, что и остальная маршрутизация. По умолчанию это делает dnsmasq через
директиву `nftset=` — но она умеет матчить только «домен + поддомены», и
работает исключительно со сборкой **dnsmasq-full** (обычный `dnsmasq` эту
директиву не поддерживает — тогда доменная маршрутизация молча ничего не
делает; `splify-doctor` теперь явно на это указывает).

Опциональный пакет **splify-dns** — свой собственный демон (`splify-dnsd`),
который встаёт перед dnsmasq как прозрачный прокси: реальные DNS-запросы и
DHCP dnsmasq продолжает обслуживать без изменений, а splify-dnsd только
подсматривает вопрос/ответ и при совпадении домена добавляет полученный IP в
тот же nft-сет — с TTL, взятым из настоящего ответа. Он умеет больше типов
правил (точный домен, домен+поддомены, wildcard `*`/`?`, regex `re:...`) и не
требует dnsmasq-full. Ставится независимо (`apk add splify-dns` /
`opkg install splify-dns`) — если пакет не установлен или архитектура ещё не
собрана, ничего не меняется: splify тихо продолжает работать через dnsmasq,
как раньше.

**Проблема общих IP (Cloudflare и другие CDN) — и как splify-dns её решает.**
Несколько разных сайтов часто сидят на одном IP из общего облачного пула
(Cloudflare раздаёт адреса динамически, без жёсткой привязки «домен = IP»).
Если просто тегать РЕАЛЬНЫЙ полученный IP в nft-сет (как делает dnsmasq
`nftset=`, и как делают внешние инструменты вроде MagiTrickle — там та же
модель), это ненадёжно: сегодня два ваших домена резолвятся в разные адреса,
а завтра могут случайно совпасть — и тогда оба поедут одним маршрутом, хотя
должны были разными.

По-настоящему точная маршрутизация «только этот конкретный сайт» обычно
решается разбором SNI прямо в трафике (без DNS) — но у этого подхода свой
минус: при включённом ECH (Encrypted Client Hello, всё чаще у Cloudflare)
настоящий SNI зашифрован и неразличим, а DNS-имя в такой ситуации видно
всегда.

splify-dns решает это иначе — через **fake-IP**: для домена, попавшего в
список (`vpn_domain`/`direct_domain`), splify-dnsd вместо настоящего адреса
отдаёт клиенту свой собственный, уникальный, персональный IP из
зарезервированного диапазона `198.18.0.0/15` (тот же приём, что у Clash/
sing-box/mihomo). Раз этот адрес закреплён splify-dns'ом за одним конкретным
доменом навсегда, коллизия становится структурно невозможной — а поскольку
решение принимается по имени в DNS-запросе (оно всегда видно в открытом
виде), ECH тут вообще не при чём. Настоящий обратный адрес подставляется
обратно через nftables (DNAT) непосредственно перед выходом пакета из
роутера — сайт получает корректный SNI и обслуживает запрос как обычно.
AAAA-ответы для таких доменов не отдаются вовсе (splify не маршрутизирует
IPv6), чтобы клиент с IPv6 не проскочил в обход через настоящий адрес.
